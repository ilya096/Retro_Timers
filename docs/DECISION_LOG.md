# Retro Timer: Decision Log

## 2026-06-25

### Unity-Проект Размещен В `UnityProject/`

- Решение: Unity-проект хранится в папке `UnityProject/` внутри корня репозитория.
- Почему проблема важна сейчас: нужно отделить Unity-generated файлы от документации и служебных файлов проекта.
- Почему выбран этот подход: `docs/` остается на верхнем уровне, а Unity-структура хранится компактно в отдельной папке.
- Какие альтернативы отклонены: Unity-проект прямо в корне репозитория, потому что это смешивает `Assets/`, `Packages/`, `ProjectSettings/` с документацией и рабочими файлами Codex.
- Ожидаемый эффект: проще поддерживать `.gitignore`, ревьюить изменения и не коммитить generated folders.

### MVP Стартует На Unity 6.3 LTS С URP 2D

- Решение: проект создан на Unity `6000.3.18f1` в Universal 2D / URP 2D конфигурации.
- Почему проблема важна сейчас: стартовая версия редактора и render pipeline влияют на камеру, VFX, 2D lighting, pixel-perfect решения и совместимость пакетов.
- Почему выбран этот подход: LTS-ветка снижает риск нестабильности, а URP 2D дает пространство для rewind VFX и визуальной читаемости клонов.
- Какие альтернативы отклонены: пустой non-URP 2D проект, потому что поздний переход на URP может затронуть материалы, камеру и VFX.
- Ожидаемый эффект: core loop можно проверять на стабильной базе без ранней миграции render pipeline.

### Минимальный Package Set Для MVP

- Решение: в MVP используем Input System, Cinemachine, Unity Test Framework, URP 2D, UGUI, Localization и 2D Tilemap Extras.
- Почему проблема важна сейчас: нужно зафиксировать стартовую техническую поверхность проекта до реализации core-фич.
- Почему выбран этот подход: эти пакеты напрямую поддерживают управление, камеру, тесты, HUD, локализацию и сборку puzzle-комнат.
- Какие альтернативы отклонены: Visual Scripting, Multiplayer Center и Unity Version Control / Collab Proxy, потому что они не нужны single-player core loop и Git-based workflow.
- Ожидаемый эффект: проект остается достаточно легким, но готовым к реализации movement, timer, rewind и clone playback.

### WebGL Сборка Для GitHub Pages Делается Без Compression

- Решение: WebGL build для GitHub Pages создается через `RetroTimers.EditorTools.WebGLBuildPipeline.BuildGithubPages`, output хранится в `UnityProject/Builds/WebGL`, а compression отключен.
- Почему проблема важна сейчас: нужно быстро раздать MVP-срез через обычный статический hosting без настройки custom headers.
- Почему выбран этот подход: GitHub Pages надежно отдает несжатые Unity WebGL файлы; `.br/.gz` сборки требуют корректного `Content-Encoding`, который Pages не настраивает на уровне репозитория.
- Какие альтернативы отклонены: коммитить WebGL build в source-ветку или использовать compressed artifacts; первое засоряет review, второе повышает риск нерабочего deploy.
- Ожидаемый эффект: feature source-ветка остается чистой, а опубликованная `gh-pages` ветка содержит только статический билд.

### MVP-Срез Публикуется Через `gh-pages`

- Решение: source-код MVP-среза опубликован в `feature/time-rewind-webgl-pages`, а WebGL artifacts опубликованы в `gh-pages` и доступны по `https://ilya096.github.io/Retro_Timers/`.
- Почему проблема важна сейчас: нужен быстрый способ дать человеку открыть и проверить текущий gameplay slice без локального Unity Editor.
- Почему выбран этот подход: GitHub Pages уже включен для репозитория и умеет раздавать статический WebGL build из branch root.
- Какие альтернативы отклонены: хранить билд в `main` или source feature-ветке; это смешивает generated artifacts с исходниками Unity.
- Ожидаемый эффект: можно отдельно ревьюить source branch и отдельно обновлять публичную playable-сборку.

### WebGL MVP-Срез Считается Стабильной Точкой Сессии

- Решение: опубликованный WebGL build 2026-06-25 считается стабильной точкой текущей сессии для `time_rewind` vertical slice.
- Почему проблема важна сейчас: нужно отделить подтвержденный playable baseline от дальнейших экспериментов с кампаниями, визуалом и финальными правилами взаимодействия клонов.
- Почему выбран этот подход: пользователь вручную подтвердил, что опубликованная версия работает; HTTP-проверка GitHub Pages показала доступность `index.html`, loader, wasm и data artifacts.
- Какие альтернативы отклонены: оставлять статус `needs_manual_retest`, потому что ручная проверка уже выполнена и срез доступен публично; считать все MVP-фичи полностью завершенными, потому что часть систем реализована только как вертикальный срез или placeholder.
- Ожидаемый эффект: следующая сессия может стартовать от стабильного WebGL baseline, а не заново выяснять состояние core loop.

### MVP `time_rewind` Реализуется Как Вертикальный Срез

- Решение: первая реализация `time_rewind` включает минимальные зависимости: движение, таймер, запись траектории, playback-клонов, задержку управления, fail-state, HUD и тестовый puzzle-сценарий.
- Почему проблема важна сейчас: isolated rewind-кнопка не проверяет главное обещание фичи; нужен сценарий, где клон помогает пройти дверь.
- Почему выбран этот подход: вертикальный срез позволяет человеку локально проверить причинно-следственную цепочку "попытка -> отмотка -> клон -> новая итерация -> выход".
- Какие альтернативы отклонены: реализовать только доменную математику или только UI-кнопку; эти варианты не доказывают, что core loop читается.
- Ожидаемый эффект: после Unity-компиляции и тестовой сцены можно проверять acceptance criteria из feature spec на одном уровне.

### `player_control_delay` Задерживает Физическое Появление Новой Итерации

- Решение: после rewind новая управляемая итерация не создается в мире сразу; она появляется только после `player_control_delay`.
- Почему проблема важна сейчас: если новый игрок появляется одновременно с прошлым клоном, их коллизии ломают старт записи и толкают игрока до получения осмысленного контроля.
- Почему выбран этот подход: цель задержки изначально состояла в предотвращении стартовой блокировки прошлых клонов новой коллизией.
- Какие альтернативы отклонены: создавать игрока сразу, но отключать управление; это не решает физическое столкновение и противоречит причине введения задержки.
- Ожидаемый эффект: прошлый клон успевает выполнить стартовый участок маршрута, а новая итерация появляется позже и не разрушает предыдущую запись.

### Задержка Появления Становится Частью Записи Клона

- Решение: если итерация появилась с задержкой, ее первый записанный кадр хранит эту временную отметку, а playback-клон остается скрытым и без коллизии до своего первого кадра.
- Почему проблема важна сейчас: иначе на следующей отмотке клон delayed-итерации появлялся бы в нулевую секунду и снова создавал стартовую коллизию.
- Почему выбран этот подход: playback должен честно повторять не только маршрут, но и момент появления итерации в таймлайне.
- Какие альтернативы отклонены: проигрывать delayed-итерацию с нулевой секунды; это делает поведение клонов нечестным и непредсказуемым.
- Ожидаемый эффект: каждая временная итерация сохраняет свой реальный старт во времени, а цепочка клонов остается читаемой.

### Текущий Игрок Имеет Физический Приоритет Над Playback-Клонами

- Решение: playback-клон не толкает текущего игрока; если игрок стоит на пути клона, клон останавливает свое воспроизведение, пока путь не будет свободен.
- Почему проблема важна сейчас: основной puzzle-use-case требует, чтобы игрок мог перепрыгнуть клона, встать перед ним и не дать ему продолжить опасный маршрут.
- Почему выбран этот подход: текущая итерация должна быть инструментом изменения последствий прошлой итерации, а не объектом, который прошлое насильно сдвигает.
- Какие альтернативы отклонены: клон как kinematic playback-объект, который толкает игрока; это ломает приоритет текущего действия и мешает использовать блокировку клона как решение.
- Ожидаемый эффект: игрок может физически вмешиваться в прошлую запись, останавливать или сдвигать клона и тем самым предотвращать парадоксальные исходы вроде падения клона в ловушку.

### Поведение Сдвинутых Playback-Клонов Проверяется Через Debug-Переключатель

- Решение: в HUD добавлен режим `Clone mode`, который переключает playback-клонов между `Recover to recording` и `Preserve displacement`.
- Почему проблема важна сейчас: сдвинутый с плиты клон в текущей реализации быстро возвращается к записанной точке, что логично для точной записи, но может противоречить ожиданию физического вмешательства игрока.
- Почему выбран этот подход: переключатель позволяет сравнить оба варианта в одном тестовом сценарии без переписывания уровня и без преждевременного финального решения.
- Какие альтернативы отклонены: сразу заменить поведение на сохранение смещения; это убрало бы возможность проверить, не нужна ли точная абсолютная запись для других пазлов.
- Ожидаемый эффект: плейтест покажет, какой режим лучше поддерживает причинно-следственную связь "игрок сдвинул клона -> результат изменился".

### MVP-Прыжок Должен Позволять Запрыгивать На Клонов

- Решение: дефолтный `jumpVelocity` игрока поднят с `9` до `12`, а generator тестового prefab явно сохраняет это значение.
- Почему проблема важна сейчас: блокировка клона требует надежно перепрыгнуть или обойти его, иначе основной use-case зависит от слишком точного тайминга и физики.
- Почему выбран этот подход: высота прыжка выше роста игрока поддерживает puzzle-сценарий "перепрыгнуть клона -> встать перед ним -> остановить опасный маршрут".
- Какие альтернативы отклонены: оставить прежний прыжок и править только уровень; это маскирует проблему, но не делает базовый movement совместимым с механикой клонов.
- Ожидаемый эффект: игрок может стабильно запрыгивать на/над клонами и использовать текущую итерацию как инструмент вмешательства в прошлую.

### `time_rewind` Делается Первой Feature Spec

- Решение: первой детализируем фичу `time_rewind`.
- Почему проблема важна сейчас: отмотка связывает таймер, смерть/парадокс, запись действий, появление клонов и победу в единый core loop.
- Почему выбран этот подход: без спецификации отмотки нельзя надежно проектировать `clone_recording_and_playback`, `delayed_clone_control` и последующие интерактивные объекты.
- Какие альтернативы отклонены: начать с движения или объектов; это проще технически, но хуже проверяет уникальное обещание игры.
- Ожидаемый эффект: команда получает дизайн-контракт для первой проверки core loop.

### Отмотка Создает Полезную Прошлую Итерацию, А Не Обычный Retry

- Решение: ручная отмотка сохраняет текущую попытку как будущего клона.
- Почему проблема важна сейчас: игрок должен воспринимать попытку как часть решения, а не как сброшенную ошибку.
- Почему выбран этот подход: fantasy фичи состоит в планировании цепочки действий нескольких версий себя.
- Какие альтернативы отклонены: обычный restart без клона, потому что он разрушает уникальность игры.
- Ожидаемый эффект: каждая попытка становится потенциальным инструментом puzzle-решения.

### Ручная Отмотка Доступна Только Пока Управляемый Клон Жив И Уровень Не Завершен

- Решение: игрок может вручную отмотать время только до фиксации смерти, победы или поражения.
- Почему проблема важна сейчас: нужно определить приоритеты между отмоткой, смертью и завершением уровня.
- Почему выбран этот подход: он сохраняет ощущение честного ввода и не позволяет отменять уже случившийся парадокс.
- Какие альтернативы отклонены: разрешать отмотку в любом состоянии или только на земле; первое размывает цену ошибки, второе делает управление слишком ограниченным.
- Ожидаемый эффект: игрок понимает, что успевшая команда отмотки срабатывает, но зафиксированная смерть уже является проигрышем.

### Цена Отмотки Выражена Через Общий Таймер И Задержку Управления

- Решение: отдельного лимита отмоток в MVP нет; цена ручной отмотки задается ростом `player_control_delay`.
- Почему проблема важна сейчас: нужно ограничить число полезных итераций без лишней мета-экономики.
- Почему выбран этот подход: таймер уже является главным ресурсом уровня и естественно ограничивает количество полезных попыток.
- Какие альтернативы отклонены: отдельный лимит отмоток, потому что он добавляет второй ресурс и усложняет раннее понимание.
- Ожидаемый эффект: игрок видит, что каждая новая итерация дороже по времени, но правило остается предсказуемым.

### При Нехватке Активного Времени Показывается Последний Клон Без Управления

- Решение: если после задержки у новой итерации остается меньше `minimum_active_time_after_delay`, игра создает последнего клона без управления, объясняет причину проигрыша и предлагает рестарт.
- Почему проблема важна сейчас: нужно превратить системный отказ в читаемый fail-state.
- Почему выбран этот подход: он показывает причинно-следственную связь между задержкой, таймером и невозможностью продолжить.
- Какие альтернативы отклонены: мгновенный game over без создания клона, потому что он хуже объясняет причину поражения.
- Ожидаемый эффект: игрок понимает, что проигрыш вызван исчерпанием полезного времени, а не произвольной остановкой уровня.

### Главный Риск Для Проверки: Авто-Отмотка Может Восприниматься Несправедливо

- Решение: первым UX-риском для плейтеста считаем восприятие авто-отмотки при истечении таймера.
- Почему проблема важна сейчас: авто-отмотка отличается от привычного поведения таймера в платформерах.
- Почему выбран этот фокус: если игрок считает авто-отмотку неожиданной, core loop будет восприниматься как непредсказуемый.
- Какие альтернативы отклонены: фокус только на ручной отмотке или только на задержке управления; они важны, но авто-отмотка сильнее ломает ожидания.
- Ожидаемый эффект: UI и tutorial будут заранее объяснять таймер как лимит полезных итераций.
