# Git Workflow For Retro Timer

## Цель

Этот документ фиксирует базовые правила работы с Git для `Retro Timer`, чтобы изменения в дизайне, коде, ассетах и документации были отслеживаемыми и не смешивались в один большой поток.

## Основные Ветки

### `main`

`main` - стабильная ветка проекта.

Правила:

- в `main` не коммитим напрямую, кроме редких мелких правок документации на самом старте проекта;
- все значимые изменения попадают в `main` через отдельную feature-ветку;
- состояние `main` должно быть рабочим: проект открывается, документация читается, критические файлы не сломаны;
- каждый merge в `main` должен иметь понятную цель.

### Feature-Ветки

Под каждую самостоятельную задачу создается отдельная ветка.

Формат имени:

```text
type/short_task_name
```

Рекомендуемые `type`:

- `feature` - новая игровая фича;
- `docs` - документация, GDD, дизайн-спеки;
- `fix` - исправление ошибки;
- `balance` - правки чисел, таймингов, сложности;
- `content` - уровни, тексты, ассеты, контентные изменения;
- `refactor` - внутренняя переработка без изменения поведения;
- `experiment` - проверка идеи, которая может быть выброшена.

Примеры:

```text
docs/time_rewind_gdd
feature/time_rewind
feature/clone_playback
feature/buttons_doors
balance/clone_spawn_delay
content/tutorial_levels
fix/paradox_death_rule
experiment/mobile_controls
```

## Базовый Рабочий Цикл

Перед началом задачи:

```powershell
git switch main
git pull
git switch -c docs/time_rewind_gdd
```

Во время работы:

```powershell
git status
git diff
git add docs/2026-06-25_time_rewind_gd-spec.md
git commit -m "Document time rewind design"
```

Публикация ветки:

```powershell
git push -u origin docs/time_rewind_gdd
```

После проверки:

```powershell
git switch main
git pull
git merge --no-ff docs/time_rewind_gdd
git push
```

Удаление локальной ветки после merge:

```powershell
git branch -d docs/time_rewind_gdd
```

## Правила Коммитов

Коммит должен быть маленьким, понятным и тематически цельным.

Хорошо:

```text
Document time rewind auto-reset rules
Add project feature index
Tune clone spawn delay values
Fix door trigger description
```

Плохо:

```text
updates
stuff
fix
many changes
```

Рекомендации:

- один коммит - одна законченная мысль;
- не смешивать дизайн, код, ассеты и баланс без причины;
- перед коммитом всегда смотреть `git diff`;
- не коммитить временные файлы, кэши, build-output и служебные папки Codex;
- если изменение рискованное, описывать причину в теле коммита.

## Правила Для Документации

Для GDD и проектных документов использовать ветки `docs/...`.

Примеры:

```text
docs/project_concept
docs/time_rewind_gdd
docs/level_design_guidelines
docs/campaign_structure
```

Документы, которые задают базовые правила проекта, должны обновляться вместе:

- `docs/project-concept.md`;
- `docs/feature-index.md`;
- feature-spec документы;
- `docs/git-workflow.md`, если меняется процесс работы.

Если новая feature-spec меняет список фич или зависимости, нужно обновить `docs/feature-index.md`.

## Правила Для Игровых Фич

Для gameplay-фич использовать ветки `feature/...`.

Перед началом реализации желательно иметь feature-spec в `docs/`.

Рекомендуемый порядок:

1. Создать или обновить GDD-спеку.
2. Создать feature-ветку.
3. Реализовать минимальный рабочий вертикальный срез.
4. Проверить базовый сценарий вручную.
5. Обновить документацию, если поведение изменилось.
6. Сделать pull request или merge в `main`.

## Правила Для Баланса

Для чисел, таймингов и сложности использовать ветки `balance/...`.

Примеры:

```text
balance/level_timer_values
balance/clone_spawn_delay
balance/tutorial_difficulty
```

Баланс-изменения должны отвечать на вопрос: какой игровой эффект мы хотим получить.

## Правила Для Экспериментов

Эксперименты делать в ветках `experiment/...`.

Правила:

- эксперимент может быть грязнее обычной feature-ветки, но не должен попадать в `main` как есть;
- после проверки результат либо переносится в нормальную `feature/...` ветку, либо удаляется;
- если эксперимент дал важное решение, оно фиксируется в документации.

## Когда Делать Pull Request

Даже если работаешь один, pull request полезен как точка самопроверки.

PR нужен для:

- крупных фич;
- изменений core-механик;
- новых GDD-спек;
- правок правил таймера, смерти, отмотки, клонов;
- изменений структуры кампании или прогрессии.

PR можно не делать для:

- мелкой опечатки;
- очевидного форматирования;
- временной правки в самом начале проекта.

## Что Я Буду Рекомендовать В Этом Проекте

- Core-механики `time_rewind`, `clone_recording_and_playback`, `clone_collision_and_interaction` вести через отдельные feature-ветки.
- Перед реализацией рискованных gameplay-систем сначала фиксировать GDD-спеку.
- Не смешивать документацию GDD и реализацию в одной ветке, если задача большая.
- Для каждого важного изменения обновлять `docs/feature-index.md`.
- На старте проекта держать `main` максимально чистой и рабочей.
- Для временных идей использовать `experiment/...`, чтобы не загрязнять историю.
